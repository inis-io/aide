# 03 - 统一错误分类（Reason）与通知去重键（DedupeKey）落地文档

## 1. 背景

两个独立但同源的「聚合语义统一」问题：

**A. 错误码不统一。** `GatewayError.Code` 是各渠道原生错误码，业务想做渠道无关的兜底（如「订单不存在就走关单补偿」）必须认识每家的码表。现状证据：

- `alipay.go:229` 已对 `ACQ.TRADE_NOT_EXIST` 做特判（关单幂等返回 nil）——需求真实存在，只是没有标准化；
- 三家「查无此单」行为不一致：支付宝走业务错误码（`ACQ.TRADE_NOT_EXIST`）、微信返回 `404 ORDER_NOT_EXIST`、PayPal 返回非 2xx（`RESOURCE_NOT_FOUND`），业务无法统一识别。

**B. 通知事件 ID 语义不统一。** `NotifyEvent.ID` 的现状：

- 微信用 `notify.Id`（同一事件重发时稳定），PayPal 用 `webhook.Id`（稳定）——可直接用于幂等；
- **支付宝 `notify_id` 每条通知都不同**（`alipay.go:368-370` 仅在 `notify_id` 缺失时退化为内容哈希），同一订单 `TRADE_SUCCESS` 重复推送时 ID 各异，业务拿 `event.ID` 做唯一约束会漏重。

## 2. 目标与非目标

### 2.1 目标

- `GatewayError` 增加标准分类字段 `Reason`，三个 Provider 各自维护错误码映射表；
- 观测与日志记录（`Observation` / `LogRecord`）同步携带 `Reason`；
- `NotifyEvent` 增加 `DedupeKey`，由 `Driver` 统一派生（不靠各 Provider 自觉），业务据此做幂等约束；
- 全部改动为**纯追加**：不改动任何既有字段语义、方法签名与返回值结构。

### 2.2 非目标

- 不做错误码映射表的「全集」：首期只收录已核实的条目，其余随联调逐步补全（映射缺失时 `Reason` 为空串，行为与现状完全一致，零风险）；
- 不做自动重试/补偿编排（`Outcome` + `Retryable` 已给出决策依据，编排在业务侧，可组合 `taskx`）；
- 不改 `NotifyEvent.Valid()` 的既有语义。

## 3. 错误分类（Reason）设计

### 3.1 核心包（`pay/error.go`）

```go
// Reason - 网关错误的标准分类；映射缺失时为空串，业务不得依赖空值之外的取值集合收敛
type Reason string

const (
	ReasonNone             Reason = ""
	ReasonOrderNotFound    Reason = "order-not-found"    // 订单/退款/转账单不存在
	ReasonAmountMismatch   Reason = "amount-mismatch"    // 金额与原单不一致
	ReasonDuplicateRequest Reason = "duplicate-request"  // 幂等冲突（网关侧判定重复提交且参数不一致）
	ReasonRateLimited      Reason = "rate-limited"       // 网关频率限制
	ReasonInvalidRequest   Reason = "invalid-request"    // 参数或状态被网关判定非法
)

// GatewayError 追加字段：
// Reason - 标准错误分类，由 Provider 按错误码映射表填写
Reason Reason

// ReasonOf - 提取错误的标准分类，非 GatewayError 或未映射返回 ReasonNone
func ReasonOf(err error) Reason
```

`ReasonOf` 用 `errors.As` 实现，供业务写渠道无关分支：

```go
if pay.ReasonOf(err) == pay.ReasonOrderNotFound { /* 走补单/关单补偿 */ }
```

### 3.2 观测链路（`pay/options.go`、`pay/driver.go`）

- `Observation` 与 `LogRecord` 各追加 `Reason Reason` 字段；
- `Driver.observe`（`driver.go:243-246`）在 `errors.As` 命中 `GatewayError` 时一并填充 `record.Reason`，日志记录同步带上。

### 3.3 Provider 映射表（各包私有）

每个 Provider 增加一个纯函数映射（形态统一，便于测试与补全）：

```go
// reasonFor - 将网关原始错误码映射为标准分类；未知码返回 ReasonNone
func reasonFor(code string) pay.Reason
```

并在 `checkAlipayResponse` / `checkResponse`（wechat、paypal）中填充 `gateway.Reason`；传输层错误（`gatewayError` 构造的）固定 `ReasonNone`。

**首期映射表**（✓ = 已核实来源，其余标注「联调确认」）：

| Provider | 原始码 | Reason | 依据 |
|---|---|---|---|
| alipay | `ACQ.TRADE_NOT_EXIST` | `order-not-found` | ✓ 现网代码特判（`alipay.go:229`） |
| alipay | `ACQ.TRADE_HAS_SUCCESS` | `duplicate-request` | 联调确认（关单时已支付） |
| alipay | `ACQ.REFUND_AMT_NOT_EQUAL_TOTAL` | `amount-mismatch` | 联调确认 |
| wechat | `ORDER_NOT_EXIST` | `order-not-found` | ✓ [官方文档](https://pay.weixin.qq.com/doc/v3/merchant/4012791879)（404） |
| wechat | `PARAM_ERROR` / `INVALID_REQUEST` | `invalid-request` | ✓ 同上文档错误码列表 |
| wechat | `268892183` | `amount-mismatch` | ✓ [官方退款错误码](https://pay.weixin.qq.com/doc/v3/merchant/4020801246)（订单或退款金额不一致） |
| wechat | `268448746` | `rate-limited` | ✓ 同上（单笔订单退款频率限制） |
| paypal | `RESOURCE_NOT_FOUND` | `order-not-found` | PayPal v2 标准错误名，联调复核 |

### 3.4 既有特判的保留

`alipay.CloseTrade` 对 `ACQ.TRADE_NOT_EXIST` 返回 nil 的幂等语义**保持不变**；Reason 是附加信息，不改变任何现有返回行为。

## 4. 通知去重键（DedupeKey）设计

### 4.1 语义

业务幂等真正需要的是「**同一业务单号 + 同一标准事件类型**只处理一次」，而不是网关的投递 ID：

- 同一订单 `TRADE_SUCCESS` 重复推送 → 键相同 → 去重生效；
- 同一订单先 `trade.pending` 后 `trade.succeeded` → 键不同 → 都正常处理；
- `event.ID` 保留网关原值，仅用于排查与对账，**不再建议作为幂等键**。

### 4.2 派生规则（收敛在 Driver，Provider 零改动）

`NotifyEvent` 追加字段：

```go
// NotifyEvent 追加：
// DedupeKey - 业务幂等去重键：业务单号（缺省退化为网关单号）+ "|" + 标准事件类型，由 Driver 统一派生
DedupeKey string `json:"dedupeKey"`
```

`Driver.ParseNotify`（`driver.go:162-177`）在 `event.Valid()` 通过后派生：

```
resource = 事件唯一资源（Trade / Refund / Transfer）
no       = firstNonEmpty(OutTradeNo|OutRefundNo|OutTransferNo, GatewayTradeNo|GatewayRefundNo|GatewayTransferNo)
DedupeKey = no + "|" + string(event.Type)
```

- 单号为空的极端情况（理论上 Valid() 已保证有资源但内部单号可能为空）退化为 `event.ID + "|" + string(event.Type)`，保证键非空；
- 派生逻辑为 `driver.go` 内一个纯函数 `deriveDedupeKey(event NotifyEvent) string`，单测直接覆盖。

### 4.3 业务接入方式（文档级）

- 持久化方案：业务表加 `(provider, dedupe_key)` 唯一索引，插入冲突即重复投递；
- 轻量方案：用 `cachex` 以 `dedupeKey` 为键做短窗口去重（注意缓存去重只是加速层，不能替代唯一索引）；
- `pay/README.md` 的「通知与 ACK」段补充说明：`DedupeKey` 为推荐幂等键，`ID` 为网关投递标识。

## 5. 安全与边界

- `Reason` 只暴露分类语义，不引入新的敏感信息；`GatewayError.Error()` 文本维持现状（不含 `Message` 与报文）；
- `DedupeKey` 含业务单号明文（与 `NotifyEvent.Trade.OutTradeNo` 等既有字段同级别），不进入 `LogRecord`（日志仍只用 `OutNoHash` 摘要）；
- 映射表只增不减；任何「改了映射导致既有业务分支行为变化」的 PR 需在描述中显式声明。

## 6. 测试要求

- 核心包：`ReasonOf` 对包装/非包装/`nil` 错误的行为；`deriveDedupeKey` 四类组合（trade/refund/transfer + 业务单号缺失退化）；`Driver.observe` 填充 `Reason` 到 Observation 与 LogRecord；
- 三个 Provider：`reasonFor` 表驱动用例（每个映射条目一例 + 未知码返回 `ReasonNone`）；`checkResponse`/`checkAlipayResponse` 产出的 `GatewayError.Reason` 正确；
- 端到端：假平台/假 SDK 下「查无单」三家统一满足 `pay.ReasonOf(err) == pay.ReasonOrderNotFound`；
- 通知：三家 `ParseNotify` 产出的 `DedupeKey` 符合派生规则，同一载荷重复解析键相同。

## 7. 任务拆解

1. `pay`：`Reason` 枚举 + `GatewayError.Reason` + `ReasonOf` + `Observation`/`LogRecord` 追加 + `observe` 填充 + 核心测试；
2. `pay`：`NotifyEvent.DedupeKey` + `deriveDedupeKey` + `ParseNotify` 接线 + 测试；
3. `alipay` / `wechat` / `paypal`：各自 `reasonFor` 映射表与接线 + 测试（三个包可并行）；
4. 文档：`pay/README.md` 补「标准错误分类」与「通知幂等键」两段说明。

## 8. 验收标准

- `go build ./... && go vet ./... && go test ./...` 全绿；
- 三家「查无此单」可用 `pay.ReasonOf(err) == pay.ReasonOrderNotFound` 统一识别，不再出现渠道专属判断；
- 支付宝同一 `TRADE_SUCCESS` 通知重复投递时 `DedupeKey` 完全一致；
- 既有公开 API 的签名与行为零变化（纯追加字段），存量调用方无需修改。
