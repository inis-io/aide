# 04 - 多币种与汇率解决方案

## 1. 问题定义

多币种支付只有两种场景，处理路径完全不同：

- **场景 A：通道原生支持扣款币种**——例如用 PayPal 收 USD。网关直接按该币种扣款、回调、退款，**不需要任何汇率计算**，业务要做的只是"别画蛇添足"。
- **场景 B：通道不支持目标币种，需要业务自行换汇定价**——例如商品按 CNY 定价，但 PayPal 账户只能收 USD。此时必须在下单前完成换汇，且汇率必须在下单瞬间锁定（买家看到的价格必须等于实际扣款金额，"支付时按实时汇率重算"在任何支付网络里都不成立）。

本方案给出两种场景的判定方法与各自的标准处理路径。前提原则（`支付能力接口工厂抽离设计方案.md` §4.2/§7.2/§10.2，不变）：

- `pay` 包不做汇率换算、不保存汇率、Provider 配置不出现汇率项；
- Provider 收到的永远只是"已经决定好币种与金额的 `Money`"；
- 汇率来源、报价与损益是业务决策。

## 2. 判定框架：先问"通道认不认这个币种"

```
定价币种/扣款币种确定后：
    通道原生支持该币种？
        ├─ 是 → 场景 A：透传（§3），全程无汇率
        └─ 否 → 场景 B：报价锁定（§4），下单前完成换汇并冻结快照
```

### 2.1 现状支持矩阵（代码事实）

| Provider | 原生可扣款币种 | 代码依据 |
|---|---|---|
| alipay | 仅 CNY（境内直连） | 响应金额解析硬编码 `CNY`（`alipay.go:217/275/308`） |
| wechat | 仅 CNY | 创建/退款/转账三处硬校验（`wechat.go:133/218/263`） |
| paypal | 任意已注册币种（透传） | 直接上送 `request.Amount.Currency.Code`（`paypal.go:119`） |

### 2.2 `pay` 侧的小改动：币种支持声明（本方案唯一进库的代码）

现状是"业务靠记忆知道哪家支持什么币种"，判定没有库内依据。增加一个**可选接口**，与既有能力模式同构：

```go
// pay/pay.go 追加：

// CurrencySupporter - Provider 可选接口：声明原生支持的扣款币种（ISO 4217 大写）
// 返回空切片表示"不限制"（以 Money.Validate 的币种注册表为准）；未实现该接口视为未知，保守按不支持处理
type CurrencySupporter interface {
	SupportedCurrencies() []string
}
```

```go
// pay/driver.go 追加：

// SupportsCurrency - 判断 Provider 是否原生支持指定币种扣款
func (this *Driver) SupportsCurrency(code string) bool
```

实现规则：

- `code` 未在 `pay` 币种注册表注册（`currencyExponent` 查不到）→ 一律 `false`；
- Provider 未实现 `CurrencySupporter` → `false`（保守，宁可走场景 B 也不误透传）；
- Provider 返回空切片 → `true`（不限制）；
- 否则查表匹配。

三个 Provider 的落地（各一行级别改动）：

- alipay / wechat：`SupportedCurrencies() []string { return []string{"CNY"} }`——顺便**收敛 `wechat.go:133/218/263` 散落的硬编码判断**：包内币种常量表只有一份，`SupportedCurrencies()` 的实现与创建/退款/转账入口校验共用同一数据源，消除"矩阵靠注释维护"的现状；
- paypal：`SupportedCurrencies() []string { return nil }`（不限制，透传）；
- 未来接入跨境直连（alipay global、微信跨境 V3）时只改各自实现，业务判定代码不动。

## 3. 场景 A：透传（通道原生支持币种）

业务直接以该币种定价并下单，`pay` 全链路零汇率参与：

- 下单：`NewMoneyMinor(amount, "USD")` → `CreateTrade`，Provider 透传；
- 对账：`NotifyEvent.Trade.Amount` 与订单金额**同币种直接比对**；
- 退款：`Driver.Refund` 已强制退款额与总额同币种（`driver.go:111`），按原币种原路退；
- 唯一注意点：**PayPal 账户侧的换汇（余额转换、提现换汇）发生在订单链路之外**，属商户与 PayPal 之间的账户行为，与 `pay` 无关；结算口径差异靠账单对账（§4.7 同一机制）。

## 4. 场景 B：报价锁定模式（需业务自行换汇）

### 4.1 角色划分

| 角色 | 职责 | 位置 |
|---|---|---|
| `pay` | 只接收已决定的扣款 `Money`，完成支付与通知 | 库（不变） |
| 报价服务 | 取价、加点、TTL、缓存、换算、产出报价快照 | 业务组件（可沉淀为 aide 顶级包，见 §5） |
| 业务收银 | 定价、持久化三件套、调 `pay` 下单、对账 | 业务系统 |

### 4.2 报价数据模型（禁止 float64）

与 `pay` 的"禁止 float64"原则一致，汇率用定点表示：

```go
// Quote - 一次汇率报价
type Quote struct {
	// From / To - 源/目标币种（ISO 4217 大写，均须在 pay 注册表注册）
	From, To string
	// Rate - 十进制字符串，最多 8 位小数：1 单位 From（主单位）= Rate 单位 To（主单位）
	Rate string
	// Source - 报价来源标识（如 "ecb" / "cnbank" / 自有报价台）
	Source string
	// MarkupBps - 已应用的加点（基点，万分之一；符号方向由业务定价策略决定，见 §4.4）
	MarkupBps int32
	// QuotedAt - 报价时间
	QuotedAt time.Time
	// TTL - 报价有效期（建议 5–10 分钟，按报价源频率配置；日频源如央行中间价可到小时级）
	TTL time.Duration
}

// Valid - 报价未过期且字段合法
func (this Quote) Valid(now time.Time) bool
```

内部计算时将 `Rate` 解析为 `rateScaled = round(Rate × 10^8)` 的 int64，解析失败或超 8 位小数的报价**拒绝使用**。

### 4.3 换算与舍入规则

```go
// Convert - 按报价把源金额换算为目标金额（同币种短路返回原值）
func Convert(source pay.Money, quote Quote) (pay.Money, error)
```

公式（`sourceMinor`、`rateScaled`、`10^targetExp`、`10^sourceExp`、`10^8` 均为整数）：

```
targetMinor = round_half_up( sourceMinor × rateScaled × 10^targetExp / (10^sourceExp × 10^8) )
```

硬性规则：

- **中间值必须用 `math/big.Int`**：`int64` 金额 × `10^8` 汇率缩放 × `10^targetExp` 必然溢出 int64；不引入第三方 decimal 依赖，标准库 `math/big` 足够；
- 舍入只许 **half-up**，与 `pay` "Provider 不得自行四舍五入修正"的口径区分：换算发生在业务定价层，舍入规则必须显式、唯一、可复算；
- **反向校验**：用同一报价把 `targetMinor` 反算回源币种，与 `sourceMinor` 偏差超过 1 个源最小单位时视为报价精度不足，返回错误（宁可拒单不出错价）；
- 同币种直接短路，不走公式。

### 4.4 报价生命周期

```
取价 → 加点 → 缓存（带 TTL）→ 下单时校验未过期 → 锁定快照 → 持久化
```

- **多源 fallback**：主源失败切备源；全部失败且缓存中无未过期报价 → **fail closed，拒绝新定价**（过期报价禁止下单，错价比拒单贵得多）；存量订单不受影响（快照已锁）；
- **加点缓冲（MarkupBps）**：在源汇率上按基点加点吸收日内波动，方向由商户角色决定（收单侧通常对卖出方向减点自保）；加点值入快照，保证可复算；
- **缓存**：推荐用 `cachex` 以 `FX-{From}-{To}` 为键、TTL 即报价 TTL 缓存当前有效报价；热点币种用 `taskx` 的 `Every` 周期任务提前刷新，避免请求时取价抖动；
- **报价源**：央行中间价/ECB 参考汇率为日频（"实时"本就不存在），商业行情源为秒级——TTL 按源特性配置，不追求伪实时。

### 4.5 订单快照三件套（持久化）

设计文档 §7.2 已要求持久化三样，本方案落到具体字段（业务订单表）：

| 字段 | 说明 |
|---|---|
| `original_amount_minor` / `original_currency` | 原定价金额与币种（如 10000 / CNY） |
| `charge_amount_minor` / `charge_currency` | 网关实际扣款金额与币种（如 1380 / USD），即传给 `pay` 的 `Money` |
| `rate` / `rate_source` / `rate_quoted_at` / `rate_markup_bps` | 汇率快照：定点字符串、来源、报价时间、加点 |

快照是**财务凭证**：落库后不可更新，争议处理与审计以它为准。

### 4.6 支付链路衔接

- 下单：`CreateTrade` 的金额用扣款币种换算结果；`IdempotencyKey` 建议派生自 `RequestFingerprint(TradeCreateRequest)`，天然含金额与币种，重复定价不会混单；
- 通知对账：`NotifyEvent.Trade.Amount` 与**扣款金额快照**比对（设计文档 §7.2 明确要求），严禁拿 USD 回调金额与 CNY 原定价直接比；
- 退款：按扣款币种金额原路退（`Driver.Refund` 强制同币种），部分退款按扣款币种计算比例，**全程不重新换汇**；汇率波动造成的退款损益入财务科目，不进支付链路；
- 查询补单：`QueryTrade` 的 `ChargedAmount` 与快照比对，同理。

### 4.7 结算对差（汇兑损益）

快照价 ≠ 网关结算价：跨境收单按**结算时刻网关牌价**结算本位币，该价下单时不可知。标准做法：

1. 用 Biller（文档 01，落地依赖）拉取网关账单/结算明细；
2. 与本地快照逐笔比对：扣款币种金额应一致，本位币入账金额的差异记**汇兑损益**科目；
3. 对差逻辑在业务财务侧，`pay` 只负责提供准确的扣款金额与账单入口。

## 5. 组件落地形态（两选一）

- **选项一（推荐，最轻）**：报价服务在业务系统内实现，`aide` 侧只落 §2.2 的 `CurrencySupporter` 小改动；本方案的 `Quote` / `Convert` 作为参考实现贴入业务代码；
- **选项二（多项目复用时）**：报价服务沉淀为 `aide` 顶级新包（如 `ratex`，与 `cachex`/`taskx` 平级）：`Source` 接口（多源 fallback）+ 定点换算 + TTL 缓存（依赖 `cachex`）+ 周期刷新（依赖 `taskx`）。**它不进 `pay` 核心、不被 Provider import、不出现在任何 Provider 配置与请求扩展里**——设计文档 "`CnyToUsdRate` 不进入 Provider 配置" 的边界不破。

明确不做：

- `pay` 核心包出现任何换算函数或汇率字段；
- Provider 请求/配置携带汇率；
- 任何形式的"支付时按实时汇率重算"。

## 6. 全链路时序（场景 B）

```
买家下单(CNY 100.00)
  → 收银服务取报价 Quote{USD/CNY 口径换算, TTL 10min}（缓存命中或取价+加点）
  → Convert → 扣款金额 USD 13.80（big.Int + half-up + 反向校验）
  → 持久化三件套（CNY 100.00 / USD 13.80 / 汇率快照）
  → pay.CreateTrade(USD 13.80) → PayPal 扣款 USD 13.80
  → 通知回调：NotifyEvent.Amount(USD 13.80) 与扣款快照比对 ✓
  → 退款：按 USD 13.80（或部分）原路退，不重算汇率
  → 月末：Biller 拉 PayPal 结算明细 → 与快照对差 → 汇兑损益入财务
```

## 7. 安全与边界

- 全链路禁止 `float64` 参与金额与汇率；换算只在业务定价层发生一次，公式与舍入唯一；
- 报价源故障不得影响存量订单（快照已锁定）；新定价 fail closed；
- 快照落库后只读，禁止 UPDATE（凭证属性）；
- `SupportsCurrency` 只是判定辅助，Provider 入口的既有币种校验（如微信 CNY 硬校验）保留作最后防线，纵深防御不撤；
- 汇率快照不含敏感信息，可按普通业务日志处理；扣款金额相关日志仍遵守 `pay` 白名单（只用 `OutNoHash` 摘要）。

## 8. 任务拆解

1. `pay`：`CurrencySupporter` 接口 + `Driver.SupportsCurrency` + 三家实现（含微信硬编码收敛）+ 测试；
2. 报价组件（业务侧或 `ratex`）：`Quote` / `Valid` / `Convert`（big.Int + half-up + 反向校验）+ 多源 fallback + TTL 缓存 + 测试（含溢出用例、过期用例、反向校验偏差用例）；
3. 收银链路：三件套持久化 + 通知/查询比对从"原金额"改为"扣款快照" + 测试；
4. 文档 01（Biller）落地后：接通结算对差，汇兑损益报表。

## 9. 验收标准

- `go build ./... && go vet ./... && go test ./...` 全绿；
- `Driver.SupportsCurrency`：alipay/wechat 仅 CNY 为真，paypal 对已注册币种为真、未注册币种为假；
- 场景 A：PayPal 收 USD 全链路无任何换算代码路径（代码走查确认）；
- 场景 B：同一报价重复换算结果完全一致（确定性）；`int64` 大额边界不溢出；过期报价下单被拒；通知金额比对命中扣款快照；
- `pay` 核心包与 Provider 配置中不出现任何汇率字段（`grep -ri "rate\|forex\|汇率" pay --include="*.go"` 除币种精度与注释外无命中）。
