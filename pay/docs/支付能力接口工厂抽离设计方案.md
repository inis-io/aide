# aide/pay：支付能力接口工厂抽离设计方案

> 文档状态：**核心协议与官方 Provider 已实施**  
> 方案版本：**V2（兼容性、安全性、扩展性加固版）**  
> 目标模块：`github.com/inis-io/aide/pay`  
> 调研来源：`pay/backend/app/spi`、三个 Provider、业务调用链与《开放聚合支付平台改造方案》  
> 编写日期：2026-08-08

V2 在原接口工厂方案上新增：实例 Registry、防静默覆盖、Pool 租约与有界缓存、结构化支付动作、严格通知验签、敏感配置与 Raw 策略、请求指纹、Provider 命名空间扩展、配置 SchemaVersion 及公共 API 兼容承诺。

## 1. 结论先行

本次不建议把 `pay/backend/app/spi` 原样复制到 aide。现有代码已经具备“能力接口 + 注册表 + SDK 客户端工厂”的雏形，但公共接口仍直接依赖：

- Gin 的 `*gin.Context`；
- pay 项目的 `BasicModel.Trade` / `BasicModel.Trans` / `BasicModel.PayGateway`；
- pay 项目的 `types.RefundOrder` 与各网关配置 DTO；
- `facade.MainDB`、全局 `DefaultStore` 和数据库缓存；
- pay 项目固定的回调路由、收银台地址、流水号生成规则与状态值；
- `float64` 金额。

这些依赖会让 aide/pay 变成 pay 项目的“代码搬家”，无法作为独立工具包复用。

推荐在 aide 中重新收敛为三层：

1. **核心协议层 `pay`**：金额、请求/结果、能力接口、错误、工厂注册表、Driver、Resolver/Pool；只依赖 Go 标准库；
2. **官方适配层 `pay/providers/*`**：支付宝、微信、PayPal 的 go-pay/gopay 适配实现；只处理网关协议；
3. **业务适配层（留在 pay 项目）**：数据库、网关选择、配置解密、费率、钱包、订单状态机、URL Policy、商户通知和审计。

最终调用形态：

```go
registry := pay.NewRegistry()
if err := wechat.Register(registry); err != nil {
	return err
}

driver, err := registry.New(ctx, "wechat", wechat.Config{
	AppID:       "...",
	MerchantID:  "...",
	APIv3KeyRef: "secret://pay/wechat/api-v3-key",
	SerialNo:    "...",
	PrivateKeyRef: "secret://pay/wechat/private-key",
	PublicKeyID: "...",
	PublicKey:   "...",
}, pay.WithSandbox(false), pay.WithSecretResolver(secretResolver))

result, err := driver.CreateTrade(ctx, pay.TradeCreateRequest{
	OutTradeNo: "202608080001",
	Mode:       pay.TradeModeQR,
	Subject:    "商品",
	Amount:     pay.NewMoneyMinor(1000, "CNY"),
	NotifyURL:  "https://example.com/api/notify/wechat/trade/gw_1",
})
```

多网关项目使用 `Resolver + Pool`，而不是全局唯一 Provider：

```go
pool := pay.NewPool(registry, databaseResolver)
lease, err := pool.Acquire(ctx, "gateway:12")
if err != nil {
	return err
}
defer lease.Release()

driver := lease.Driver()
```

## 3. 现状问题清单

### 3.1 可复用性问题

1. 接口参数是 pay 项目的 GORM 模型，其他项目无法实现或调用；
2. 通知接口接收 `*gin.Context`，把 aide 强制绑定到 Gin；
3. Provider 通过 `DefaultStore()` 获取全局数据库存储，未初始化直接 panic；
4. 回调 URL 由 Provider 拼接 pay 项目固定路由；
5. 支付宝 PC `return_url` 硬编码为 `https://inis.cn`；
6. Provider 内生成 TradeNo/RefundNo，业务方无法在调用前持久化幂等键；
7. 注册表保存 Provider 单例，不是“配置 → 独立实例”的工厂模式；
8. 同一进程多商户、多网关凭据依赖 `gatewayId + DefaultStore` 隐式切换，实例隔离不明确。

### 3.2 正确性与可靠性问题

1. `Money` 使用 `float64`，支付金额可能出现精度与四舍五入边界问题；
2. SPI 方法没有 `context.Context`，内部大量使用 `context.Background()`，调用方取消、超时和链路追踪失效；
3. Provider 在业务落库之前已经向支付宝/微信/PayPal 返回 success；后续数据库更新失败时，网关不会继续重试；
4. PayPal 将 CNY 换算为 USD，但回调事件返回 USD 数值；现有业务用它直接与 CNY 原订单金额比较，币种不一致；
5. PayPal 的缓存 key 直接拼接 `clientId + secret`，不是摘要，凭据会长期存在于 map key；
6. `DbGatewayStore` 缓存没有 TTL，配置修改后的失效依赖外部主动调用，但当前 SPI 调用链中没有稳定的失效闭环；
7. PayPal `CHECKOUT.ORDER.APPROVED` 在通知解析阶段执行 Capture，验签解析与有副作用操作混在一起；
8. 微信通知虽然发起主动查单，但现有判断主要检查通知里的 `TradeState`，应明确校验查询响应的真实终态；
9. 状态使用任意字符串，Provider 之间存在 `pending/processing/fail/closed` 映射漂移风险；
10. `Register` 不校验 nil、空名称和能力一致性。

### 3.3 安全边界问题

1. aide 不应负责数据库中凭据的加解密或保存；
2. 错误与日志不能输出 private key、APIv3 key、secret、证书全文；
3. `Raw` 需要保留排障价值，但必须由业务方决定是否持久化及如何脱敏；
4. NotifyURL/ReturnURL/CancelURL 的 SSRF 与白名单策略属于业务系统，不应由 Provider 猜测；
5. 网关回调的 HTTP success 必须在业务事务成功后发送。

## 4. 设计目标与非目标

### 4.1 设计目标

1. 核心包不依赖 Gin、GORM、pay 模型和全局数据库；
2. `Factory` 为 Provider 唯一创建入口，注册表支持官方与外部 Provider；
3. 一个 Driver 对应一套明确凭据，天然支持多商户、多网关与沙箱/生产隔离；
4. 金额统一使用最小货币单位整数，不在核心协议中使用 `float64`；
5. 所有网关调用显式携带 `context.Context`；
6. 订单号、退款号、转账号、通知 URL 由调用方显式传入；
7. Provider 只完成 SDK 调用、签名验签、加解密和响应标准化；
8. 通知解析与 HTTP ACK 分离，业务成功后才返回 success；
9. 能力按小接口组合，不支持的 Provider 无需空实现；
10. 提供 Resolver/Pool，支持业务方从数据库、配置中心或密钥服务动态加载多套网关配置；
11. 提供标准错误分类、重试提示与原始网关错误码；
12. 官方 Provider 使用同一套契约测试，不做默认联网测试；
13. Provider 使用实例 Registry 显式装配，重复注册不能静默覆盖；
14. Pool 使用租约保护在途请求，并以容量、TTL 和 LRU 约束资源；
15. 支付动作结构化，不向业务端返回待直接执行的任意 HTML/script；
16. 通知只有完成验签、时间窗校验和解密后才能产生事件；
17. 敏感配置、Raw、日志、指标与审计统一遵循默认脱敏；
18. 公共 API、配置 Schema 和 Provider 扩展具有明确兼容策略。

### 4.2 非目标

- 不在 aide/pay 中保存订单、退款、转账或网关配置；
- 不实现商户、费率、钱包、结算、审核、路由权重与熔断；
- 不实现商户 Webhook 投递，可靠通知应由业务方配合 `taskx`；
- 不生成业务流水号；
- 不负责 ReturnURL/NotifyURL 白名单与 SSRF 策略；
- 不负责汇率来源、报价与损益，FX 属于业务决策；
- 不内置完整收银台或 HTTP Controller；
- 第一阶段不实现分账；
- 对账账单只预留能力接口，首期不实现下载器。

### 5.1 为什么 Provider 拆成子包

- `pay` 核心协议保持轻量，不直接导入三套 SDK；
- 使用方可只引入需要的 Provider；
- Provider 包导入核心 `pay`，通过 `Register(registry)` 显式登记 Factory，不产生循环依赖；
- 外部 Provider 与官方 Provider 使用完全相同的扩展方式。

使用全部官方 Provider：

```go
registry := pay.NewRegistry()
if err := all.Register(registry); err != nil {
	return err
}
```

只使用微信：

```go
registry := pay.NewRegistry()
if err := wechat.Register(registry); err != nil {
	return err
}
```

支付库不依赖包 `init()` 的隐式副作用。这样一个进程可以同时持有不同 Provider 集合的 Registry，测试、插件和多租户模块之间不会互相覆盖。为简单接入可以提供进程级 `DefaultRegistry()`，但官方 Provider 不自动写入它，且重复注册仍然返回错误。

## 6. 核心接口

### 6.1 Provider 与能力小接口

```go
// Provider - 支付提供者基础接口
type Provider interface {
	Name() string
	Capabilities() []Capability
	Close() error
}

type TradeCreator interface {
	CreateTrade(ctx context.Context, request TradeCreateRequest) (TradeResult, error)
}

type TradeQuerier interface {
	QueryTrade(ctx context.Context, request TradeQueryRequest) (TradeResult, error)
}

type TradeCapturer interface {
	CaptureTrade(ctx context.Context, request TradeCaptureRequest) (TradeResult, error)
}

type TradeCloser interface {
	CloseTrade(ctx context.Context, request TradeCloseRequest) error
}

type Refunder interface {
	Refund(ctx context.Context, request RefundRequest) (RefundResult, error)
}

type RefundQuerier interface {
	QueryRefund(ctx context.Context, request RefundQueryRequest) (RefundResult, error)
}

type Transferer interface {
	Transfer(ctx context.Context, request TransferRequest) (TransferResult, error)
}

type TransferQuerier interface {
	QueryTransfer(ctx context.Context, request TransferQueryRequest) (TransferResult, error)
}

type NotifyParser interface {
	ParseNotify(ctx context.Context, request NotifyRequest) (NotifyEvent, error)
	NotifyResponse(kind NotifyKind, decision NotifyDecision) NotifyResponse
}

// Biller - 账单下载预留能力，首期只定接口不做官方实现
type Biller interface {
	FetchBill(ctx context.Context, request BillRequest) (BillResult, error)
}
```

能力标识至少包含：

```go
const (
	CapTradeCreate  Capability = "trade:create"
	CapTradeQuery   Capability = "trade:query"
	CapTradeCapture Capability = "trade:capture"
	CapTradeClose   Capability = "trade:close"
	CapRefund       Capability = "refund:create"
	CapRefundQuery  Capability = "refund:query"
	CapTransfer     Capability = "transfer:create"
	CapTransferQuery Capability = "transfer:query"
	CapNotifyTrade  Capability = "notify:trade"
	CapNotifyRefund Capability = "notify:refund"
	CapNotifyTransfer Capability = "notify:transfer"
	CapWebhook      Capability = "notify:webhook"
	CapBill         Capability = "bill:fetch"
)
```

`Capabilities()` 与实际接口实现必须双向校验：Registry 构造 Driver 时执行运行时校验，契约测试再做完整覆盖。声明了能力但未实现接口，或实现接口却未声明能力，构造阶段直接返回 `ErrInvalidProvider`，不能等到资金请求发生时才暴露。

### 6.2 Factory 与实例级注册表

```go
// ConfigInput - 强类型配置与动态 Raw 二选一
type ConfigInput struct {
	Value any
	Raw   json.RawMessage
}

// Factory - Provider 工厂；options 已完成默认值归一化。
type Factory func(
	ctx context.Context,
	input ConfigInput,
	options OpenOptions,
) (Provider, error)

type Registry struct { /* mutex + factories */ }

func NewRegistry() *Registry
func (this *Registry) Register(name string, factory Factory) error
func (this *Registry) MustRegister(name string, factory Factory)
func (this *Registry) Replace(name string, factory Factory) error
func (this *Registry) Names() []string
func (this *Registry) New(ctx context.Context, name string, config any, options ...Option) (*Driver, error)
func (this *Registry) OpenRaw(ctx context.Context, name string, raw json.RawMessage, options ...Option) (*Driver, error)
```

约定：

- 名称统一转为小写并 TrimSpace；
- `Register` 对空名称、nil Factory、重复名称返回错误；`MustRegister` 只用于启动期静态装配，失败时 panic；
- 同名 Provider 不允许静默覆盖，只有调用方显式执行 `Replace` 才能替换；
- `Registry.New` 把强类型配置放入 ConfigInput.Value，不经过 JSON 序列化，避免 SensitiveString 被脱敏后无法构造 Provider；
- `Registry.OpenRaw` 只用于 Resolver/配置中心等动态场景，Factory 必须检查 Value/Raw 恰好提供一种并严格拒绝未知字段；
- Factory 必须完整验证配置，配置缺失返回 `ErrInvalidConfig`；
- Factory 不能访问全局数据库，也不能从环境变量偷偷补凭据；
- New 失败不降级到其他 Provider。

支付 Provider 属于资金安全边界。这里有意不沿用其他 aide 子包“同名后注册覆盖”的宽松规则，避免恶意依赖、测试包或 Go 初始化顺序静默劫持 Provider。`Registry` 应作为依赖注入给 Pool；默认注册表只用于单体简单场景，不是强制全局单例。

### 6.3 Driver

业务方不需要反复做类型断言，Driver 统一检查能力并分发：

```go
type Driver struct {
	provider Provider
}

func (this *Driver) Name() string
func (this *Driver) Supports(capability Capability) bool
func (this *Driver) Provider() Provider
func (this *Driver) CreateTrade(ctx context.Context, request TradeCreateRequest) (TradeResult, error)
func (this *Driver) QueryTrade(ctx context.Context, request TradeQueryRequest) (TradeResult, error)
func (this *Driver) CaptureTrade(ctx context.Context, request TradeCaptureRequest) (TradeResult, error)
func (this *Driver) CloseTrade(ctx context.Context, request TradeCloseRequest) error
func (this *Driver) Refund(ctx context.Context, request RefundRequest) (RefundResult, error)
func (this *Driver) QueryRefund(ctx context.Context, request RefundQueryRequest) (RefundResult, error)
func (this *Driver) Transfer(ctx context.Context, request TransferRequest) (TransferResult, error)
func (this *Driver) QueryTransfer(ctx context.Context, request TransferQueryRequest) (TransferResult, error)
func (this *Driver) ParseNotify(ctx context.Context, request NotifyRequest) (NotifyEvent, error)
func (this *Driver) NotifyResponse(kind NotifyKind, decision NotifyDecision) NotifyResponse
func (this *Driver) Close() error
```

不支持的调用统一返回 `ErrUnsupportedCapability`，不要求 Provider 提供空实现。

支付调用不采用链式可变上下文：每次操作都显式传入完整请求，便于审计、重试和幂等，也避免链式对象被跨 goroutine 误用。

## 7. 金额模型

### 7.1 禁止 float64

```go
// Money - 金额值对象
type Money struct {
	Minor    int64    `json:"minor"`
	Currency Currency `json:"currency"`
}

type Currency struct {
	Code     string `json:"code"`
	Exponent uint8  `json:"exponent"`
}

func NewMoneyMinor(minor int64, currency string) Money
func ParseMoney(value string, currency string) (Money, error)
func RegisterCurrency(code string, exponent uint8) error
func (this Money) MajorString() string
func (this Money) IsPositive() bool
func (this Money) SameCurrency(other Money) bool
func (this Money) Add(other Money) (Money, error)
func (this Money) Sub(other Money) (Money, error)
```

示例：

- CNY `10.01` → `Minor=1001, Exponent=2`；
- USD `0.30` → `Minor=30, Exponent=2`；
- JPY `100` → `Minor=100, Exponent=0`。

`ParseMoney` 用字符串运算解析，不经过 float64。核心包内置常用 ISO 4217 币种精度表；CNY、USD、JPY 等已知币种的 exponent 必须与标准值一致，调用方不能构造 `CNY + Exponent=3`。未知币种必须先显式注册 exponent，禁止默认猜测两位小数。金额加减必须校验币种和 exponent 相同，并检查 int64 溢出。

零金额、负金额是否允许属于具体操作的请求校验规则：创建支付、退款和转账默认要求正数；查询结果可以表达零值，但 Provider 不得自行取绝对值或四舍五入修正非法输入。

### 7.2 Provider 边界

- 微信直接使用 `Money.Minor`，并验证币种小数位符合微信接口要求；
- 支付宝使用 `MajorString()` 生成 `total_amount/refund_amount/trans_amount`；
- PayPal 使用 `MajorString()` 生成两位或币种规定精度的 value；
- Provider 不自动做 CNY/USD 汇率换算。

PayPal 如果需要收取 USD，业务方必须在下单前完成换汇，并持久化：

- 原订单金额与币种；
- 网关实际扣款金额与币种；
- 汇率快照与报价时间。

通知金额应与“网关实际扣款金额”比较，不能再拿 USD 回调金额直接与 CNY 原订单比较。

### 8.1 交易创建

### 8.2 Provider 专属扩展参数

标准 DTO 只放三个及以上 Provider 共同拥有且语义一致的字段。支付宝花呗分期、微信场景信息、PayPal shipping 等专属能力使用命名空间扩展，不继续膨胀公共结构体：

```go
type Extensions map[string]json.RawMessage

request.Extensions, err = pay.SetExtension(
	request.Extensions,
	"alipay",
	alipay.TradeOptions{TimeoutExpress: "15m"},
)
```

Provider 只能读取自己的命名空间；存在本 Provider 不认识的字段时返回 `ErrInvalidRequest`，不能静默忽略。禁止使用无约束的 `map[string]any`，也禁止把 gopay SDK 类型泄漏到核心包。

`Metadata` 仅供调用方做本地关联，默认不发送给网关；Extensions 是明确参与网关请求的参数，两者不得混用。

### 8.5 幂等与请求指纹

- TradeNo、RefundNo、TransferNo 是业务幂等主键，必须在调用网关前持久化；
- `IdempotencyKey` 在网关原生支持时透传，不支持时仍用于本地审计与请求指纹；
- 核心包提供确定性 `RequestFingerprint`，不包含 Metadata、Raw 与敏感字段；
- 相同业务号再次调用时，业务方必须比较请求指纹；金额、币种、收款人或目标订单不同应返回 `ErrIdempotencyConflict`；
- aide/pay 不保存幂等记录，持久化和唯一约束仍由业务项目负责；
- 支付、退款、转账出现网络未知状态时遵循“原业务号查询确认后再重试”，不得由 Driver 自动重新出款。

### 8.6 状态枚举

核心包统一状态，不直接暴露网关原始状态：

```go
const (
	StatusPending    Status = "pending"
	StatusProcessing Status = "processing"
	StatusSucceeded  Status = "succeeded"
	StatusFailed     Status = "failed"
	StatusClosed     Status = "closed"
	StatusUnknown    Status = "unknown"
)
```

TradeStatus、RefundStatus、TransferStatus 保持独立类型，不用一个无上下文的 Status 覆盖三种资源。常量字符串允许未来增加新值；反序列化遇到未知值必须保留原值，不能映射为 failed。原始状态和错误码保留在 `GatewayStatus` / `GatewayError.Code`，原始响应是否保留由 RawCapturePolicy 决定。

公共请求结构体加入不可导出的 `noUnkeyedLiterals` 标记并提供构造函数，强制外部调用方使用字段名或构造器。这样未来追加可选字段不会因为外部无字段名复合字面量而造成源码不兼容。

## 9. 通知解析与 ACK

### 9.1 框架无关请求

```go
type NotifyRequest struct {
	Kind    NotifyKind  `json:"kind"`
	Method  string      `json:"method"`
	Headers http.Header `json:"-"`
	Query   url.Values  `json:"-"`
	Body    []byte      `json:"-"`
}

type NotifyEvent struct {
	ID                string       `json:"id"`
	Type              EventType    `json:"type"`
	Provider          string       `json:"provider"`
	Trade             *TradeEvent  `json:"trade,omitempty"`
	Refund            *RefundEvent `json:"refund,omitempty"`
	Transfer          *TransferEvent `json:"transfer,omitempty"`
	OccurredAt        time.Time    `json:"occurredAt"`
	VerifiedAt        time.Time    `json:"verifiedAt"`
	VerificationKeyID string       `json:"verificationKeyId"`
	Raw               *RawPayload  `json:"-"`
}

type NotifyResponse struct {
	StatusCode int
	Header     http.Header
	Body       []byte
}
```

TradeEvent、RefundEvent、TransferEvent 分别使用 TradeStatus、RefundStatus、TransferStatus，并携带各自业务号、网关号、金额与原始网关状态。NotifyEvent 三个资源字段必须恰好一个非 nil，避免统一 Status 丢失“支付成功、退款成功、转账成功”的对象语义。

### 9.2 验证后才返回事件

`ParseNotify` 的强制处理顺序是：

```text
限制请求体大小 → 选择验签证书/Key → 验证签名 → 校验时间窗 → 解密 → 解析事件
```

- 验签、证书或解密失败只返回 `ErrVerifyFailed`，绝不返回可供业务处理的 NotifyEvent；
- 不设计 `Verified bool`，避免调用方忘记判断；能返回事件就代表 Provider 已完成协议要求的真实性验证；
- Provider 协议包含时间戳时必须校验允许偏差，默认五分钟，可通过 OpenOptions 收紧；
- `VerificationKeyID` 记录证书序列号或 Key ID，支持证书轮换和审计，但不记录证书正文；
- HTTP Controller 在构造 NotifyRequest 前限制 Body 大小，Provider 内部再次校验，形成双层保护；
- 客户端 IP 不能代替签名验证；是否信任反向代理头由业务系统决定；
- aide/pay 只生成稳定事件 ID，跨进程重放拦截依靠业务数据库唯一约束。

### 9.3 三种 ACK 决策

```go
const (
	NotifyAccept NotifyDecision = "accept" // 验签成功且业务已提交
	NotifyRetry  NotifyDecision = "retry"  // 内部临时故障，希望网关重试
	NotifyReject NotifyDecision = "reject" // 签名或报文非法
)
```

Provider 只负责把决策编码成网关要求的响应：

- Alipay：`success` / `fail` 文本；
- WeChat：V3 JSON success/fail；
- PayPal：合适的 HTTP 状态与 JSON body。

业务控制器的正确顺序：

```go
event, err := driver.ParseNotify(ctx, request)
if err != nil {
	write(driver.NotifyResponse(request.Kind, pay.NotifyReject))
	return
}

if err := service.ApplyGatewayEvent(ctx, event); err != nil {
	write(driver.NotifyResponse(request.Kind, pay.NotifyRetry))
	return
}

write(driver.NotifyResponse(request.Kind, pay.NotifyAccept))
```

严禁 Provider 在 `ParseNotify` 内写 HTTP 响应。

### 9.4 PayPal APPROVED/CAPTURE 拆分

`CHECKOUT.ORDER.APPROVED` 解析为 `trade.approved` 事件，不在解析函数中自动 Capture。业务层根据事件调用 `CaptureTrade`，成功后等待 `PAYMENT.CAPTURE.COMPLETED`，或主动查单确认。

这样可以：

- 避免 Webhook 重放触发不可控副作用；
- 对 Capture 做独立幂等与重试；
- 让 ParseNotify 保持“验签 + 解析”的稳定边界；
- 更容易使用离线 fixture 测试。

### 9.5 事件幂等

`NotifyEvent.ID` 优先使用网关事件 ID；没有事件 ID 时，以 Provider + Kind + 业务号 + 网关号 + 原始报文摘要构造稳定 ID。aide/pay 只返回 ID，不保存消费记录；业务方必须以该 ID 或业务单号做唯一约束。

### 9.6 原始报文策略

```go
type RawCaptureMode string

const (
	RawCaptureNone     RawCaptureMode = "none"
	RawCaptureRedacted RawCaptureMode = "redacted"
	RawCaptureFull     RawCaptureMode = "full"
)

type RawPayload struct {
	ContentType string
	Body        []byte
	Truncated   bool
}

type RawCapturePolicy struct {
	Mode     RawCaptureMode
	MaxBytes int64
}
```

默认 `RawCaptureNone`；调试场景可显式启用 Redacted，Full 只允许调用方明确开启。所有模式都有长度上限，Raw 永不进入 `Error()`、默认日志和 JSON 序列化。官方 Provider 必须提供字段级脱敏器，至少覆盖私钥、secret、token、Authorization、银行卡号、账号、手机号和证件信息。

## 10. Provider 配置

### 10.1 通用构造选项

```go
type OpenOptions struct {
	Sandbox          bool
	Client           *http.Client
	Logger           Logger
	Timeout          time.Duration
	Clock            Clock
	SecretResolver   SecretResolver
	Observer         Observer
	RawCapture       RawCapturePolicy
	NotifyMaxBody    int64
	NotifyClockSkew  time.Duration
}
```

- `http.Client` 可注入代理、TLS、Transport 与测试 RoundTripper；
- nil Client 使用带合理超时、响应体大小限制和安全重定向策略的默认客户端，不允许无限超时；
- Logger 为窄接口，日志字段必须脱敏；
- Clock 主要用于通知时间、缓存和测试，不允许 Provider 到处直接调用 `time.Now()`。
- 生产 Provider Endpoint 由实现固定且只允许 HTTPS；自定义 Endpoint 只能通过显式测试选项开启，普通配置不能把请求导向任意地址；
- 跨域重定向不得转发 Authorization、Cookie 或 Provider 签名头；
- OpenOptions 后续扩展只增加可选字段，不改变现有默认安全语义。

### 10.2 敏感配置

Provider 配置中的私钥、APIv3Key、ClientSecret、证书私钥等字段使用 `SensitiveString` 或 `SecretRef`，不使用可被 `%+v` 直接打印的裸字符串：

```go
type SecretRef string

type SensitiveString struct { /* 不导出明文 */ }

func NewSensitiveString(value string) SensitiveString
func (this SensitiveString) Reveal() string

type SecretResolver interface {
	ResolveSecret(ctx context.Context, ref SecretRef) ([]byte, error)
}
```

- `SensitiveString.String()`、`GoString()`、日志编码与普通 JSON 编码固定输出 `[REDACTED]`；
- 数据库、KMS、Vault 和环境变量读取由业务方实现 SecretResolver，aide/pay 不保存主密钥；
- Resolver 返回的明文配置只在 Factory 构造期间短暂存在，不进入 Pool key、错误、指标或日志；
- Pool 的配置摘要使用 SHA-256，不能拼接明文 secret；
- 能使用 `[]byte` 的敏感材料在构造完成后主动覆盖，Go string 无法可靠擦除的限制必须在 README 中说明；
- 证书轮换通过 Definition.Version 触发新 Driver 原子替换，不在旧实例上原地修改密钥。

## 11. Resolver 与多网关 Pool

### 11.1 Definition

```go
type Definition struct {
	Name          string          `json:"name"`
	Config        json.RawMessage `json:"config"`
	Sandbox       bool            `json:"sandbox"`
	Version       string          `json:"version"`
	SchemaVersion uint16          `json:"schemaVersion"`
}

type Resolver interface {
	Resolve(ctx context.Context, key string) (Definition, error)
}
```

`key` 是业务方自己的网关标识，可以是数据库 ID、租户网关 UUID 或配置中心路径。aide/pay 不解释它。

### 11.2 Pool

```go
type Pool struct { /* 键控锁 + 有界 LRU/TTL + 租约计数 */ }

type Lease interface {
	Driver() *Driver
	Release()
}

func NewPool(registry *Registry, resolver Resolver, options ...PoolOption) *Pool
func (this *Pool) Acquire(ctx context.Context, key string) (Lease, error)
func (this *Pool) Invalidate(key ...string)
func (this *Pool) Clear()
func (this *Pool) Close() error
```

规则：

1. 相同 key + Version + SchemaVersion 复用同一 Driver；
2. `Acquire` 增加租约，调用方必须 defer Release；Version 变化时先创建新实例并原子替换，旧实例标记 retiring，最后一个租约释放后才 Close；
3. 缓存 key 不包含明文 secret；配置摘要使用 SHA-256；
4. 并发首次加载使用键控锁，避免重复创建 SDK 客户端/token；
5. Resolver 返回错误不使用旧配置静默兜底，是否容灾由业务方决定；
6. Pool 不设置全局默认 Resolver，不存在未初始化 panic；
7. Pool 默认启用最大条目数、空闲 TTL 与 LRU 回收，避免 SaaS 多租户场景无限持有 SDK 客户端和 token；
8. Invalidate/Clear/Close 都先禁止新租约，再等待或异步回收存量租约，Close 必须幂等；
9. 进程关闭可配置 DrainTimeout，超时后返回仍在使用的实例数，不悄悄强制中断在途支付。

标准使用方式：

```go
lease, err := pool.Acquire(ctx, "gateway:12")
if err != nil {
	return err
}
defer lease.Release()

result, err := lease.Driver().CreateTrade(ctx, request)
```

pay 项目可实现：

```go
type GatewayResolver struct { /* MainDB */ }

func (this *GatewayResolver) Resolve(ctx context.Context, key string) (pay.Definition, error) {
	// 查询 PayGateway、解密 Config，Version 使用 updateAt 或配置 hash。
}
```

数据库与 AES 信封加密仍留在 pay 项目，不进入 aide。

### 11.3 配置版本与轮换

- Version 标识某一网关实例的配置修订，推荐使用数据库 updateAt 加配置密文摘要；
- SchemaVersion 标识 Provider 配置结构版本，Factory 对不支持版本返回 `ErrUnsupportedConfigVersion`；
- 密钥、证书、商户号或沙箱环境变化必须产生新 Version；
- 新 Driver 完整初始化成功后才能替换旧实例，初始化失败保持旧实例服务在途请求，但新的 Acquire 返回错误还是继续旧版由业务方通过明确的 PoolFallbackPolicy 决定；默认不静默使用旧凭据；
- Pool 不缓存 Resolver 返回的明文配置，仅保留不可逆摘要、版本和已构造 Driver。

## 12. 错误模型

```go
var (
	ErrProviderNotFound      = errors.New("pay: Provider 未注册")
	ErrInvalidProvider       = errors.New("pay: Provider 能力声明无效")
	ErrUnsupportedCapability = errors.New("pay: Provider 不支持该能力")
	ErrInvalidConfig         = errors.New("pay: Provider 配置无效")
	ErrInvalidRequest        = errors.New("pay: 支付请求无效")
	ErrDuplicateProvider     = errors.New("pay: Provider 已注册")
	ErrIdempotencyConflict   = errors.New("pay: 幂等请求参数冲突")
	ErrUnsupportedConfigVersion = errors.New("pay: Provider 配置版本不受支持")
	ErrVerifyFailed          = errors.New("pay: 通知验签失败")
	ErrGatewayRejected       = errors.New("pay: 网关拒绝请求")
	ErrGatewayUnavailable    = errors.New("pay: 网关暂时不可用")
)

type GatewayError struct {
	Provider  string
	Operation string
	Code      string
	Message   string
	Retryable bool
	Outcome   Outcome
	Cause     error
}
```

约定：

- 支持 `errors.Is/As`；
- `Error()` 不拼接完整 Raw，不泄露凭据或敏感响应；
- `Retryable` 仅表示技术上可重试，不替业务方决定是否重复扣款/出金；
- 创建支付、退款、转账的重试必须复用同一个业务号；
- 网关明确拒绝、参数错误、签名错误不可自动重试；
- 网络超时、限流、5xx 可标记 Retryable，但出金类操作应先 Query 再决定是否重试。

错误分类增加 `Outcome`：`known-failed`、`known-succeeded`、`unknown`。Retryable 只描述技术故障是否可能恢复，Outcome 描述本次资金操作是否已经产生结果，两者不能混用。转账、退款和 Capture 收到 timeout 时默认 OutcomeUnknown，业务方必须查询确认。

## 13. 公共 API 兼容与扩展策略

### 13.1 版本承诺

- M1 合并前允许调整 API；首个正式发布版本后遵循语义化版本；
- 已发布接口不直接新增方法，新能力通过可选小接口扩展，例如 HealthChecker、CertificateReloader；
- 导出的状态、能力、模式和错误码一旦发布不改变原有语义；新增字符串常量属于兼容变化，未知值必须保留；
- 公共请求使用构造函数、字段名初始化和 noUnkeyedLiterals，允许后续追加可选字段；
- Provider 配置使用 SchemaVersion 迁移；不兼容的公共协议随 aide 主模块升级到 `github.com/inis-io/aide/v2/pay`，不在原 API 中偷偷改变语义；
- 核心包不得暴露 gopay、Gin、GORM 或某个 Provider 的 SDK 类型。

### 13.2 可选能力演进

Provider 基础接口保持最小且稳定。健康检查、证书热加载、账单、分账等以后都通过新小接口加入，Driver 通过类型断言和 Capability 探测，不要求已有第三方 Provider 重新编译实现无关方法。

Capabilities 是运行时描述，接口实现是真实能力。官方和第三方 Provider 都必须通过共享契约测试，禁止“声明支持但调用只返回不支持”。

### 13.3 可观测性与审计扩展

OpenOptions 可注入窄接口 Observer，提供开始、结束、耗时、Provider、操作、结果分类和关联 ID；不直接依赖 OpenTelemetry。Observer 接收到的字段必须经过核心白名单构造，不能包含请求体、Raw、密钥、完整账号或 Authorization。业务方可用该接口接入 metrics、trace 与审计系统。

核心库不自动记录完整支付请求。日志默认只包含 Provider、Operation、OutNo 脱敏摘要、GatewayCode、Outcome、Retryable 和 Duration。

## 15. 与 aide 其他子包的关系

### 15.1 taskx

aide/pay 不自动启动异步任务。业务方可使用 taskx 编排：

- 支付/转账状态轮询；
- Capture 重试；
- 商户 Webhook 投递；
- 账单下载；
- 补偿扫描。

任务必须使用确定性 TaskID，例如 `pay:capture:{tradeNo}`，Handler 仍需业务幂等。

### 15.2 logx

通过窄 Logger 接口注入，不直接依赖全局 `logx.Log`。日志只记录 Provider、Operation、业务号、网关错误码与耗时，禁止记录凭据和完整支付报文。

### 15.3 cachex

SDK Client/Token 的生命周期由 Driver/Pool 管理，不用 cachex 保存带私钥的配置。业务查询结果缓存由业务方决定。

## 16. 从 pay/spi 到 aide/pay 的迁移映射

| 当前写法 | 新写法 | 说明 |
|---|---|---|
| `spi.Get(scene)` | `pool.Acquire(ctx, gatewayKey)` + `lease.Driver()` | 按具体网关实例解析，并以租约保护在途请求 |
| `spi.GetCreator(provider)` | `driver.CreateTrade(ctx, request)` | Driver 统一能力检查 |
| `CreateTrade(gatewayId, Trade, domain, way)` | `CreateTrade(ctx, TradeCreateRequest)` | 去模型、去 domain、显式 URL |
| `Refund(gatewayId, Trade, RefundOrder, domain)` | `Refund(ctx, RefundRequest)` | 退款号由业务方预生成 |
| `Transfer(gatewayId, Trans, domain)` | `Transfer(ctx, TransferRequest)` | 业务模型映射为 DTO |
| `TradeClose(gatewayId, tradeNo)` | `CloseTrade(ctx, TradeCloseRequest)` | context 贯穿 |
| `HandleXxxNotify(*gin.Context, gatewayId)` | `ParseNotify(ctx, NotifyRequest)` | Gin 留在业务 Controller |
| Provider 内 `ctx.String/JSON(success)` | `NotifyResponse(kind, decision)` | 业务提交后才 ACK |
| `DefaultStore()` | `Resolver + Pool` | 无全局 panic |
| `BasicModel.PayGateway.Config` | `Definition.Config` | 解密与数据库留在业务方 |
| `Money{float64}` | `Money{Minor int64}` | 与 pay 项目 P4 金额分迁移一致 |

### 16.1 pay 项目应保留的代码

- `PayGateway`、Trade、Refund、Trans 等 GORM 模型；
- 网关配置的信封加密与解密；
- GatewayResolver；
- 商户权限、网关选择、优先级、权重和熔断；
- 订单状态机、退款额度、审核与幂等事务；
- 费率、钱包、结算、SSE；
- 商户 Webhook 与 taskx 编排；
- URL 白名单与 SSRF 校验；
- Gin Controller 与网关 ACK 写出。

### 16.2 应移动到 aide 的代码

- Provider 能力接口和注册表；
- 框架无关的支付 DTO、Money、状态和错误；
- Alipay/WeChat/PayPal SDK 客户端创建与配置校验；
- 下单、查单、Capture、关单、退款、转账等网关协议调用；
- 回调验签、解密、事件解析和 ACK 编码；
- 网关状态到标准状态的映射；
- Provider 契约测试与离线通知 fixture。

## 17. 测试策略

### 17.1 核心包

- 实例 Registry 登记、重复拒绝、显式 Replace、Names 排序、非法 Factory 与 Registry 隔离；
- Driver 能力探测和 `ErrUnsupportedCapability`；
- Money 的正负、零值、标准币种 exponent、未知币种注册、溢出与格式化；
- Extensions 命名空间、未知字段拒绝和 RequestFingerprint 稳定性；
- PaymentAction 单一动作约束，FormAction 不接受 script、HTML 和非 HTTP(S) URL；
- 错误 `errors.Is/As` 与敏感内容不泄露；
- Pool 并发只创建一次、Version/SchemaVersion 替换、租约释放、TTL/LRU、Invalidate、Drain 与幂等 Close；
- context 取消和 deadline 透传；
- NotifyDecision 到响应的确定性编码；
- SensitiveString 的 String/GoString/JSON/日志脱敏和 RawCapture 长度上限。

### 17.2 Provider 契约套件

一套共享契约检查：

1. Name 与注册名一致；
2. Capabilities 无重复且与实现接口一致；
3. 请求校验不触网；
4. 所有操作透传 context；
5. 错误能分类为配置、请求、网关拒绝、暂时不可用；
6. Raw 不进入 Error 文本；
7. Close 幂等；
8. 沙箱与生产地址选择正确；
9. 通知验签失败绝不返回事件，成功事件包含 VerificationKeyID 和 VerifiedAt；
10. 未知扩展、非法金额、幂等号缺失在触网前失败；
11. timeout 的资金操作返回 OutcomeUnknown，不在 Driver 内自动重试；
12. Observer 只能收到白名单脱敏字段。

### 17.3 Provider 单测

- SDK 再包一层最窄内部接口，使用 fake SDK，不做默认联网测试；
- Alipay：QR/WAP/PC/Barcode、退款、关单、转账状态映射、URL encoded 通知验签 fixture；
- WeChat：分制金额、Native/H5、退款、关单、转账、通知验签解密 fixture；
- PayPal：订单创建、币种格式、Capture、Webhook 验签参数、事件类型映射；
- 所有通知测试精确断言 ACK 状态码、Header 与 Body；
- 私钥、secret、APIv3 key 不出现在错误、日志、Pool key、指标和快照中；
- 通知 fixture 覆盖过期时间戳、错误证书、重复事件、超大 Body、截断报文和密钥轮换。

### 17.4 安全与模糊测试

- 对 Money.Parse、Extensions、支付宝表单参数、微信通知解密和 PayPal Webhook 解析执行 fuzz；
- 使用 race detector 验证 Pool Acquire/Release/Invalidate/Close 与证书轮换；
- 故障注入覆盖 DNS/连接/读取超时、429、5xx、响应截断和 context cancel；
- 验证 HTTP 重定向不会把 Authorization、Cookie 或签名头带到其他域名；
- 使用 canary secret 贯穿错误、日志、Raw、Observer，测试任何输出中都不存在该值；
- 转账/退款/Capture 的超时测试必须断言不自动二次发起资金请求。

### 17.5 集成测试

真实沙箱测试使用 build tag：

```bash
go test -tags=integration ./pay/providers/alipay
go test -tags=integration ./pay/providers/wechat
go test -tags=integration ./pay/providers/paypal
```

凭据只从环境变量读取，默认 `go test ./...` 永不联网。生产凭据不用于自动测试。

## 21. 需要评审确认的决策

1. **包名**：按本次指定使用 `aide/pay`，不使用 `payx`；
2. **金额**：直接采用 minor int64，不兼容当前 float64 API；
3. **Provider 分包**：官方实现放 `pay/providers/{alipay,wechat,paypal}`，核心包不暴露 SDK 类型；
4. **多网关模型**：使用 Resolver/Pool，不提供单一全局 `pay.Pay` 活动实例；
5. **FX**：PayPal 不在 Provider 内按静态汇率自动换汇，业务方负责并保存快照；
6. **通知 ACK**：必须由业务层提交成功后输出，Provider 只编码响应；
7. **流水号**：TradeNo/RefundNo/TransferNo 全部由调用方预生成；
8. **高级支付宝模式**：首轮迁移保留 Barcode、BusinessQR、App/OrderCode，避免能力倒退；
9. **账单能力**：首期只定义 Biller，不实现真实下载；
10. **依赖版本**：gopay 跟随当前稳定版维护，由 `go.mod` 记录已验证版本以保证构建可复现；
11. **注册表安全**：改用实例 Registry，重复注册默认失败，只允许显式 Replace；
12. **Pool 生命周期**：调用方使用 Acquire/Release 租约，版本切换和关闭不打断在途请求，并启用容量与 TTL；
13. **支付动作**：QR、Redirect、Form、SDK 使用结构化对象，禁止返回待直接执行的任意 HTML/script；
14. **通知安全**：验签、时间窗和解密全部通过后才返回事件，不暴露 Verified bool；
15. **敏感数据**：支持 SecretRef/SecretResolver，Raw 默认关闭，日志和 Observer 使用白名单脱敏字段；
16. **扩展机制**：Provider 专属参数使用命名空间 Extensions，不使用 map[string]any；
17. **兼容策略**：公共接口只通过可选小接口扩展，配置带 SchemaVersion，不兼容协议随 aide 主模块升级到 `github.com/inis-io/aide/v2/pay`；
18. **幂等策略**：业务号、IdempotencyKey、RequestFingerprint 三层校验，未知资金结果先查询再重试。

以上十八项确认后再进入代码实施，可以避免开发中途反复调整公共 API。第 11～18 项是本轮针对兼容性、安全性和扩展性的升级基线，建议作为 M1 的强制验收条件，而不是后续优化项。
